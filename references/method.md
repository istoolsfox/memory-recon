# 方法说明：为什么做记忆对账

## 背景

一个用了两个多月的 agent 工作区，从产品 A 迁到产品 B。迁移报告写的是"能带走的都带走了"：281 条记忆、密钥、MCP 配置、技能。

三个月后，用户问起一件事："那个帮别人改 issue 的流程，你放哪儿了？"

搜遍新工作区的 289 个记忆文件、全部项目文档——零命中。

## 一次真实对账的数据

| 维度 | 数量 |
|---|---|
| 会话 | 790 |
| 真人输入 | 3279 |
| 带决策信号的输入 | 451 |
| 明说"记住 / 记一下 / 沉淀" | 61 |
| 最后筛出长期有效的决定 | 25 |
| 已覆盖 | 22 |
| 部分覆盖 | 2 |
| 缺失 | 1 |

那 1 条缺失，恰好就是用户要找的：一套六阶段的修 bug 流程，从选题到发车共 19 道工序。它当年只在对话里说过一遍，没有任何人把它写成文件。迁移时按"文件名"搬东西，自然就漏了。

## 结论：事实丢不了，过程会丢

三个机制叠在一起：

1. **迁的是文件，不是对话。** 记忆库是某个时间点的快照，里面只有结论，没有"怎么得出"。
2. **结论天然会被写下来。** 用户拍板时通常会补一句"记住"，模型就写一篇记忆。
3. **过程天然不会。** 用户问"流程是什么"时，回答只活在那一轮对话里；除非当场说"沉淀成文档"，否则没人写。

所以对账时，**优先级最高的不是那些没见过的结论，而是那些带步骤的东西**：流程、判据、验证方法、排错顺序。

## 缺口长什么样

一个典型的缺失条目，特征是这样的：

- 它回答的是"怎么做"，不是"是什么"
- 它有三步以上
- 它是用户主动问的（"你现在做 X 的流程是什么"）
- 它当时以对话形式给出，用户点头认可，然后继续干活

反过来，一次性资料的特征是：

- 某个临时端口、某个登录方式
- 某篇文章的链接
- 某次任务的中间数字

判据只有一条：**下次会话还会不会用到。**

## 判定流程

1. 机器先筛：决策词表 + 实体覆盖度，输出候选表，覆盖低的排前面。
2. 人再判：每条问"下次用不用"和"是结论还是过程"。
3. 只补过程：事实类如果已经覆盖，不重复搬；过程类缺失，优先补。
4. 写回：补进记忆库并加索引，否则下次还得再扫。

## 局限

- **覆盖率只认英文/数字实体。** 纯中文主题会被判成 0.00，必须人工确认。
- **它找不出"用户从没说过记住、也没问过流程"的隐性知识。** 那种只能靠定期回看。
- **它不判断对错。** 记忆里可能记着一条早就过期的结论，对账只回答"有没有"，不回答"还对不对"。
- **只能扫结构化会话库。** 没有留存的对话（比如纯语音、已删除的会话）救不回来。

## 一句话

**迁移搬得走文件，搬不走对话；对话里最值钱的，是那些没人想起来写下来的步骤。**
